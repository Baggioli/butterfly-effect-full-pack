## 1. 现象（交接记录）

CURRENT_STATE：曾观察到「展开故事」失败、角色卡保存成功。需复测建档→故事→任务完整链路。

前端路径（`public/onboarding.js`）：
1. `confirm()` 先 `persist()` 角色卡，再 `generate()`
2. `generate()` POST `/api/ai` `mode=plan`
3. 失败时回 `phase=card`，角色卡仍在；原先用**同一句**「这次故事没有完成…」覆盖服务端具体错误

## 2. 失败分支枚举（源码证据）

### 2.1 服务端 `worker/api.js` plan 路径（修复前）

| 分支 | 触发条件 | 修复前用户可见 |
|------|----------|----------------|
| 鉴权/来源/未配置 | 401/403/503 | 有明确文案 |
| 目标缺失 | 400 | 有明确文案 |
| Ollama `/api/show` 失败 | 抛「未找到所选本地模型…」 | **吞掉** → 「私人规划服务暂时不可用」 |
| 远程模型拦截 | 抛远程标记错误 | **吞掉** |
| `/api/chat` 非 2xx | 抛调用失败 | **吞掉** |
| `done_reason=length` / `done=false` | 抛「返回未完成」 | **吞掉** |
| `JSON.parse` 失败 | `SyntaxError` | 「返回内容不完整」 |
| `TimeoutError`（180s） | 超时 | 「生成超时」 |
| `validateStory` 抛错 | 结构/字段缺失等 | **吞掉** → 同上模糊文案 |

根因（**代码实锤，非推断**）：`catch` 把绝大多数 `Error`（含 `validateStory` 的明确中文）折叠成一句本地模糊 502；前端 `catch` 又再次覆盖为固定句，服务端即便返回了细分文案也进不了 UI。

### 2.2 `validateStory` 修复前实际规则

- 四幕、字段非空、每幕 quests 1–3、每任务 steps 恰好 3
- **并未**硬校验「第一章恰好 2 个 + 今天：/本周：」或「narrative≥60」——这两条只在 plan **prompt** 里
- 因此「前缀/字数导致 validateStory 抛错」在**旧代码**上是**弱推断**；更硬的是错误吞没 + 超时/截断/坏 JSON/结构不全

### 2.3 前端

- 角色卡在生成前已保存：**属实**
- 无独立「重试」文案，确认按钮文案不变
- 浏览器 200s abort 与服务端 180s 超时都可能触发，但文案不区分

## 3. 真实模型复测

| 项 | 结果 |
|----|------|
| 本机资源 | 约 15GB RAM，可用约 3–5GB；8 CPU；无 GPU |
| Ollama | 已用官方脚本安装；`ollama serve` 监听 `127.0.0.1:11434` |
| 拉模型 | **失败**：`ollama pull qwen2.5:1.5b` 因沙箱 DNS 将 Cloudflare R2 解析到非公网 `198.18.0.1`（`redirect target not allowed`） |
| 结论 | **未能**对真实 Ollama 模型跑通 plan 端到端；**不能**用本机 CPU 小模型冒充生产 32b 验收 |
| 历史旁证 | `reports/chat-story-real.json` 曾有虚构档案 plan **成功**（约 112s，含「今天：/本周：」）；说明生产链路过得去，失败更可能是间歇超时/截断/偶发结构问题 + 错误不可诊断 |

合成档案约定：若后续有授权机器复测，只用明显虚构 profile（如「虚构测试甲」），禁止使用 `data-private/`。

## 4. 修复内容

### 4.1 `worker/api.js`

- `normalizeStoryDraft`：安全归一化（补「今天：/本周：」、第一章多余任务裁到 2、步骤>3 裁到 3、今天/本周顺序对调）；**不编造**用户事实或叙事
- `StoryValidationError` + 规则码：`CHAPTER_COUNT` / `CHAPTER1_QUEST_COUNT` / `CHAPTER1_PREFIX` / `QUEST_STEPS` / …
- 第一章硬校验：恰好 2 任务且前缀正确（在 normalize 之后）
- `narrative≥60`：**仍不硬失败**（避免短叙事误杀；prompt 继续要求）
- plan/adjust 失败分流：`PLAN_TIMEOUT` / `PLAN_BAD_JSON` / `PLAN_TRUNCATED` / `PLAN_SCHEMA(+rule)` / `PLAN_MODEL` / `PLAN_UNKNOWN`，均 `retryable:true`，文案强调角色卡已保存
- 校验失败时 **自动修复重试 1 次**（把 rule + message 回灌模型）
- 服务端 `console.error` 结构化 JSON 日志

### 4.2 `public/onboarding.js`

- 展示服务端/异常的具体 `message`（Abort → 超时文案）
- 失败后主按钮改为「重新展开故事」，并提示角色卡已保存在本机

### 4.3 测试

- 更新 `test-ai.mjs` 夹具以符合第一章规则
- 新增 `test-plan-story.mjs`（**标明模拟接口，非真实模型**）：normalize、各规则码、免重试归一化、修复重试、超时/坏 JSON/截断/结构失败
- `npm test` / `npm run build` / `npm run validate`：**通过**

## 5. 剩余风险

- 生产仍依赖 DGX 上 `qwen2.5:32b`；本环境未复现真实失败样本
- 自动修复会多一次最长约 180s 调用，极端负载下总等待更长
- 需在授权独立端口/目录上用真实 32b 再跑一次虚构档案 plan，核对日志中的 `code`/`rule`
