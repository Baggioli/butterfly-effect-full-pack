# 人生推演引擎 · 技术方案与排期 v0（开发，2026-10-24）

对应 Backlog v1.12 §1.5 / P0-11/12/13 / R 组。结论：**同意产品方向**（结构化差距 + 规则/参数层 + 大模型做理解与叙事），不做纯提示词一次生成。

## 1. 数据结构
- **RoleFacts**：已确认事实 `{key, value, source: user|confirmed, confirmedAt}`；未知项显式 `unknown`，供 R1 引用核对。
- **GoalTree**：大目标 → 阶段目标 → 小目标，`{id, level, text, targetDate?, parentId, status}`。
- **GapAssessment**：固定维度（能力、资质/证书、经验、人脉/作品、收入、可投入时间）各 `{level 0–4, evidence[], factRefs[], assumption?}`。由大模型抽取、受枚举与 JSON schema 约束；**用户可确认/修改**，确认后作为推演输入缓存。
- **ParamTable（带版本）**：每维度×难度的基础周期区间、每周小时弹性系数、保持现状漂移系数、收入区间带（按行业/角色，初版手设、宽区间），全部可调、可回放。
- **Projection（带版本）**：`{inputsHash, paramVersion, nodes[{tRange, reason, dependsOn, stateStatusQuo, stateAction}], milestones[{tRange, dependsOn}], income{low, high, conditions[]}, assumptions[], unknowns[], tasks{today[], week[]}, diffFromPrev}`。
- **ExecutionLog**：任务完成/中断/反馈，作为重算输入和后续校准数据。

## 2. 分工
1. **大模型①理解**：角色卡与自述 → GapAssessment（temperature 0，枚举约束，必须引用 factRefs）。
2. **规则层（确定性）**：节点数量与时间、里程碑区间、两条轨迹的状态、收入区间都由 Gap × ParamTable × 每周小时计算得出，并输出节点理由模板（如「证书差距 3 级 × 每周 4 小时 → 约 10–14 周」）。
3. **大模型②叙事**：把骨架写成四幕叙事、细化今天/本周任务、润色节点理由。**不得改数字**，由校验器比对；不一致就打回或回退到模板文案。
4. **校验器**：R1 事实引用、R3 绝对词与区间检查、R6 投资/医疗/法律目标附专业意见提示。

## 3. A2 耗时预估（DGX qwen2.5:32b，待实测）
- Gap 抽取约 20–40s；规则层 <1s；骨架 + 今日任务约 40–60s 可出。
- 四幕叙事约 80–120s，总 P90 预计 150–220s，有可能超过 200s。
- **建议从一开始就拆分**：先返回骨架 + 两条线 + 今日任务（目标 P90 ≤ 90s），叙事异步补齐，前端显示「故事正在补全」。A6 按拆分后的两段分别记 P50/P90。

## 4. 定时重算
- 在 DGX A2 目录内跑独立 worker（systemd timer 或进程内调度），**不进生成队列**：日重算 02:00–05:00（Asia/Shanghai），周重算周日夜间。
- 日重算**只用规则层**：按执行数据推进进度、平移节点；变化说明用模板（「因为完成 X，Z 提前约 N 天」）。周重算可选调用小模型（7b）润色，低优先级；若遇到生成锁就延后，不抢白天的队列。
- **前置依赖**：A2 现在的会话和档案都存在内存里，重启就丢，必须先做服务端持久化（DGX 本地 SQLite/文件，不出 DGX）。

## 5. R4 一致性阈值（建议）
同一输入重复 5 次：
- Gap 各维度等级 5 次中 ≥4 次一致，且最大差不超过 1 级；
- 节点数量 5/5 一致，里程碑集合一致；
- 节点时间中点偏差 ≤ ±15% 或 ±2 周（取较大）；
- 收入区间上下界偏差 ≤ ±10%。
- 用户确认 Gap 之后，规则层是确定性的，偏差应为 0；R4 主要考的是抽取这一步的稳定性。

## 6. 排期（工作日，单人开发估算）
- **阶段 0（1 天）**：schema、ParamTable v0、A2 服务端持久化。
- **阶段 1（3–4 天）**：Gap 抽取、规则引擎、骨架 + 今日任务接口、最简两条线页面、6 组合成画像（易/中/难各 2）测 R1–R3 → **第 4–5 个工作日 demo 可看**。
- **阶段 2（4–5 天）**：叙事异步补齐、日/周重算、变化说明、R4–R6、A6 20 次压测 → **第 9–10 个工作日 R 组验收（R7 除外）**。
- R7 取决于 Micheal 的 3 个真实画像，时间另计。

## 7. 风险与需 Micheal 拍板
1. **收入区间的数据来源**：初版参数谁定？建议先用宽区间并标「示例校准」，后续用执行数据校准；收入预测也需要法务过一遍措辞。
2. **是否加「确认差距评估」这一步**：多一屏，但可信度和 R4 稳定性明显更好。开发建议加。
3. **服务端存档**：推演、重算、校准都需要在 DGX 本地保存角色卡和执行记录（不外传），需要 Micheal 认可。
4. **「保持现状线」的语气**：避免制造焦虑，需要产品给文案底线。
5. **模型速度**：32b 在 DGX 上偏慢；闭测期是否允许骨架用 7b、叙事用 32b。
6. **定位措辞**：v1.12 用了「预测」，与此前「不预测命运」相反，上公网前需要法务确认。
